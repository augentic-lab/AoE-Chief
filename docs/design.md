# AoE Chief 研究任务设计 v3

Oct 31, 2026 · @Tianchi

## 结论

研究任务就是一个普通的委托任务。和代码任务相比只多两样东西：交付物是一份 `memo.md`，完成检查是一个核对引文的脚本。你在对话里谈定问题，说「交给 chief」；Chief 推进、检查、找另一个模型审查；最后你读 memo 开头的一句话结论，需要时再往下读。

不新增合同文件，不新增验收层级，chief.py 不用改。

## 为什么要做

今天把研究交给 agent，Chief 帮不上忙。研究没有可执行的检查，而 Chief 的自动继续和交叉审查都要先有检查结果才会启动。结果就是：什么时候算完由 AI 自己说了算，引文真不真只能你自己去核对。

## 对照设计目的

| 设计目的 | 研究任务怎么做 |
|---|---|
| 我只定义任务、验收结果 | 和代码任务一样只在两处需要你：开头谈定，结尾读 memo。中间的问题走现有的决策队列 |
| 「完成」要可信，不靠 AI 自己说 | 检查脚本自己抓取原文，核对每条摘录确实存在；另一个模型审查 memo 是否回答了问题、是否说过头 |
| 长任务能持续 | memo 边做边写，本身就是进度；加上现有的 progress.md 和换新会话 |
| 交接没有摩擦 | 说「交给 chief」即可。研究需要的信息（问题、服务的决定、停止条件）都写在 goal 里，不另外填表 |
| 模型可以替换 | 规则是纯文本，检查脚本不调用任何模型；写作和审查由谁来做，按现有的 tool / review_engine 配置 |
| 让大脑更清楚 | memo 由浅入深：一句话结论 → 至多 3 条理由 → 引证。你通常只读第一行 |

## 工作流

1. **对话**：和 AI 谈定要研究什么、为哪个决定服务、做到什么程度就停。
2. **交接**：说「交给 chief」。AI 按 handoff.md 的「研究任务」一节写合同：
   - `goal` 写清问题、服务的决定、停止条件、已经排除的方向，并要求先读 `~/aoe-chief/rules/research.md`；
   - `checks` 是 `python3 ~/aoe-chief/tools/research_check.py research/<id>/memo.md`；
   - `test_first: false`（计划已在对话里谈定）。
3. **推进**：worker 检索、阅读、写 memo。检查不过时，Chief 把失败项发回去让它继续，跟代码任务一样。
4. **审查**：检查通过后，另一个模型读 memo，挑出没回答的问题、说过头的结论、明显漏掉的反方。
5. **验收**：你读结论。认可就 `chief close`，有意见就 `chief nudge` 退回。

研究默认用「交给 chief」，不用「收编」：研究要读大量网页，上下文涨得快，只有委托任务会换新会话。

## memo 格式

```markdown
# <要回答的问题>

结论：<一句话，直接回答问题，并给出对决定的建议>

## 理由
- <论断> [1]
- <论断> [2][3]

## 不确定与没查到
- <哪些没查清，为什么>

## 来源
[1] https://...
> 原文逐字摘录，保留原语言

[2] https://... (手动)
> 摘录（付费墙、登录页等脚本抓不到的来源标「手动」，由你验收时查看）
```

## 检查脚本做什么

`tools/research_check.py`：只用标准库，不调用模型，退出码 0 表示通过。

- memo 存在，有「结论：」一行，有「理由」和「来源」两节；
- 正文引用的每个 `[n]` 都在「来源」里有链接和摘录；
- 抓取每个链接，把空白、引号和大小写归一化之后，摘录必须逐字出现在原文中；标「手动」的来源跳过核对。

另外几个要求：

- **抓取结果按 URL 缓存。** 缓存放在 `$AOE_CHIEF_HOME/research-cache/`，worker 写不到这里，这样每轮只抓新的链接。
- **只抓公网的 http/https。** 拒绝本机和内网地址，因为检查是以你的身份运行的。
- **输出简短。** 失败项列在前面；最后一行固定写成 `FAIL: 摘录未找到 [2][5]; 缺少结论` 这样的确定写法，好让 Chief 的卡住检测能识别「反复同样失败」。

它拦得住编造的引文，拦不住「引文是真的但撑不起结论」。后者交给审查模型，以及你读 memo 时自己判断。

## 要做的改动

| 文件 | 内容 |
|---|---|
| `tools/research_check.py` | 上面的检查，约 100 行 |
| `rules/research.md` | worker 的研究规则：先写结论；一条论断对应一个可核对的来源；没打开过的页面不引用；到了停止条件就停 |
| `rules/handoff.md` | 加一节「研究任务」：合同怎么写，研究默认用委托而不是收编 |

## 试点

1. **worker 能上网（2026-10-31 已探针验证）。** 用 Chief 的启动方式（`aoe add --tool ... --launch`）起了三个会话：
   - Codex 0.165：内置检索和打开网页可用；shell 里的 curl 被沙箱挡住（DNS 解析失败），研究只能用内置工具。
   - Claude（claude-mix）：WebSearch、WebFetch、curl 都可用，auto mode 自动放行。默认模型 glm-5.3 的搜索结果偏旧，报出的最新版本号是错的；切到 Opus 5.5 后，同样的搜索给出了正确结果。研究任务的 Claude worker 要用 Claude 模型。
   - agy 1.4.12：search_web 可用；没有抓取网页的工具；curl 可用，但每次都弹审批菜单，在 Chief 里会变成「需要你」。
   - 跑检查的主机本身能访问公网。

   结论：worker 用 Codex，或者用 Claude 模型的 Claude；agy 不适合无人值守的研究。
2. 用一个真实问题跑一次，例如「各 agent CLI 如何恢复会话、压缩上下文，Chief 的会话轮换该不该改用原生恢复」。
3. 记下两件事：检查有没有误报；有没有错误一路漏到你那里。根据实际漏掉的东西再决定补什么，不提前设计。

## 暂不做

v2 里的这些先不做，等试点证明确实需要再加：

- Verification Snapshot（对代码任务也有价值，作为独立事项另议）；
- 结论知识库。
